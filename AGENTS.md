# Working in this repository

## Stack, pinned

- Expo SDK **54** (`expo@~54.0.36`), React Native 0.81, React 19.1, expo-router 6, TypeScript 5.9.
- Android only. There is no iOS code path and `app.json` has no `ios` section.
- Before writing app code, read the versioned docs at https://docs.expo.dev/versions/v54.0.0/ —
  the SDK moves quickly and the API surface is version specific.

## Layout that matters

- `app/` — expo-router screens.
- `src/` — TypeScript app logic (state providers, PIN, SQLite history, theme).
- `modules/quiet-vpn/` — the local Expo module holding all native code. This is where the
  product actually lives: a `VpnService` that filters DNS.
- `browser-extension/` — the same lists in front of a browser (Chrome, Edge, Brave, Opera, Vivaldi,
  Firefox, Safari). Plain JavaScript on purpose, no dependencies; `scripts/build.mjs` turns one
  source tree into a package per target, including the `declarativeNetRequest` rulesets.
- `browser-extension/store/` — the store submission material: listing copy, permission
  justifications, reviewer notes and the listing images, with `test/store.test.cjs` holding it to the
  stores' limits and to this repository.
- `website/` — the landing page for both halves, published to GitHub Pages. Plain HTML, one
  stylesheet, two scripts, no build step, and it links the packages from the latest release rather
  than storing copies of them.
- `android/` and `ios/` are generated by `expo prebuild` and are **gitignored**. Never edit them by
  hand; change `app.json`, a config plugin, or the module instead.

## Rules

- Keep the app's claims honest. If a feature cannot be delivered on Android (for example, a password
  on the system uninstall dialog), document the constraint instead of faking it.
- The DNS/IP wire helpers (`DnsWire.kt`, `IpWire.kt`, `DomainRules.kt`) must stay free of Android
  imports so they remain covered by JVM unit tests. Add a test with any change to them.
- Anything that weakens protection (stopping the tunnel, changing lists, clearing stats, releasing
  the uninstall lock) must require the PIN, and the check belongs in native code.
- A PIN is mandatory. `startAsync` refuses to run without one, removing the PIN stops the tunnel and
  releases the uninstall lock, and the setup wizard is a gate rather than a suggestion. Never add a
  path that leaves the app filtering without a PIN in place.
- Hiding the launcher icon (`LauncherVisibility`) toggles the `LauncherAlias` activity-alias created
  by `plugins/withLauncherAlias.js`. It must never disable `MainActivity`: an app whose launcher
  activity is disabled cannot be started by anything - not its own notification, not a deep link, not
  adb - and doing that locked users out of their own app once already.
- The name lives in `expo.name` alone, and the identifiers match it: package `dev.quiet.app`, Kotlin
  package `expo.modules.quietvpn`, `modules/quiet-vpn`, `QuietVpn` as the JavaScript module name, storage
  keys prefixed `quiet`. Changing the *package* name is the expensive one - a fresh install for every
  user, plus the device owner command in `docs/UNINSTALL-PROTECTION.md`.
- Never hardcode the app's name in a user-visible string. It comes from `expo.name` in `app.json` and is
  read at runtime - `APP_NAME` from `src/lib/app-name.ts` in JavaScript, `applicationInfo.loadLabel` in
  Kotlin, `runtime.getManifest().name` in the extension - so the label can be made discreet with one
  line. The shipping label is deliberately neutral. The extension's name and version are injected at
  build time from the same `app.json`.
- The browser extension's matcher (`browser-extension/src/common/domains.js`) is a port of
  `DomainRules.kt`, and `browser-extension/test/domains.test.cjs` repeats the Kotlin `DomainRulesTest`
  cases. Change one, change the other in the same commit.
- `browser-extension/src/common/lists.js` is the extension's only list catalogue: the build and the UI
  both read it. The lists themselves come from `modules/quiet-vpn/android/src/main/assets/blocklists/`,
  so the app and the extension block the same domains from one file.
- The extension may not call the network at runtime. A feature that needs a list has that list
  generated at build time, and the UI says when a list was not included in the build.
- Everything that weakens protection in the extension (switching the shield off, changing lists or the
  allowlist, clearing statistics) must ask for the PIN, and the check belongs in
  `browser-extension/src/background/background.js`, not in the screens.
- The website may not claim anything the repository cannot back up. `node website/check.mjs` enforces
  the parts that can be checked mechanically (links resolve, download names match the builds, the
  domain counts are the lists, no tracker or CDN appears in the markup) and it runs in CI. A new
  claim on the page should come with a check, or with a sentence saying where the number came from.
- The site never commits binaries. Downloads point at the release attached by CI, so there is one copy
  of each artefact and one place to update it.
- Store credentials are never committed, never printed and never written to a file. They are read from
  the environment; `browser-extension/scripts/publish-store.mjs` names every one of them and
  `store/README.md` says where each comes from. A missing credential stays a skip rather than a
  failure, so a release can run the publishing step before the store accounts exist.
- A store listing is a claim about the software, so it is checked like one: the copy against each
  store's character limits, the images against the exact pixel sizes the stores require, the numbers
  in those images against the blocklists they came from, and the manifest's own description against
  the 132-character limit Chrome's review checklist enforces.
- Keep every way back in working while the icon is hidden: the ongoing notification and
  `quiet://open` (both through `VaultActivity`), Recents, `adb shell am start`, and the
  `*#*#78438#*#*` secret code. Hiding is refused when there is no reachable way back
  (`canHide`: notifications enabled and a resolvable launch intent).

## Verify before claiming done

```sh
npm run typecheck
npx expo export -p android --output-dir /tmp/export   # proves the JS bundle builds
npx expo prebuild -p android
cd android && ./gradlew :quiet-vpn:testDebugUnitTest :app:assembleDebug
```

And for the browser extension, from `browser-extension/`:

```sh
npm test        # includes the Kotlin test cases, ported
npm run build   # validates every ruleset and manifest before packaging
npm run smoke   # loads the build in a real browser (reports itself skipped if there is none)
```

And for the website, from the repository root:

```sh
node website/check.mjs
```
